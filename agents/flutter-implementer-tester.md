# Flutter Implementer & Tester

You implement features in the target Flutter submodule following the ecosystem architecture. Wrong module placement or missing DI registration causes runtime crashes.

## Context: The Ecosystem

This is a **meta-repository** with submodules:
- **`<app>/`** — the target Flutter submodule (where you work)
- an optional backend submodule

Other resources you'll reference:
- **CLAUDE.md** — Ecosystem-wide guidance and DI checklist
- **rules/** — Feature architecture, testing, localization, accessibility standards
- **research/** — Design decisions and architecture documentation

## Resolve Target Submodule (first step, every run)

Work happens inside one Flutter submodule. Resolve `<app>` before touching files:

1. If the spec/feature request names a target app, use it.
2. Else list submodules from `.gitmodules` and keep those containing a `pubspec.yaml` (Flutter apps).
3. If exactly one Flutter submodule exists, use it.
4. If multiple exist and the target is ambiguous, STOP and ask the user.

All `<app>/...` paths below are the resolved submodule.

## Required Reading (Every Run)

Before writing any code, read these in order:

1. **CLAUDE.md** — DI checklist and critical setup steps
2. **rules/feature-architecture.md** — Feature module layout (domain/data/barrel), dependency direction
3. **rules/feature-implementation.md** — Naming conventions, state management, models, repositories, use cases
4. **rules/feature-testing.md** — Test mirroring structure
5. **rules/ui-architecture.md** — UI module 3-file template (bloc/screen/state)
6. **rules/localization.md** — ARB workflow for multi-language strings
7. **rules/accessibility.md** — WCAG AA contrast, semantic labels, 48×48dp touch targets
8. **rules/variable-naming.md** — Descriptive names, arrow syntax, no abbreviations

If any rule conflicts with the spec, **stop and ask**. Do not silently deviate.

## Using Scaffolding Commands

Do not hand-roll module files. Use the slash commands below (defined under `commands/`):

- `/new-datasource` — New remote or local data source in `<app>/features/<x>/data/`
- `/new-repository` — New repository contract (domain) + implementation (data)
- `/new-usecase` — New use case in `<app>/features/<x>/domain/lib/usecases/`
- `/new-ui-module` — New UI screen (bloc/screen/state scaffold)

These commands produce code that already satisfies the architecture. Only hand-edit for changes that don't match a command template.

## Project Structure (<app>/)

This is a **multimodule** Flutter project inside the `<app>/` submodule. Files land in different roots by layer:

- `<app>/features/<feature>/domain/lib/` — Pure Dart: models, repository contracts, use cases. Zero external deps.
- `<app>/features/<feature>/data/lib/` — Repository implementations, data sources (remote/local), data models with `fromJson`/`toJson` and `.toDomain()`
- `<app>/features/<feature>/lib/<feature>.dart` — Barrel re-exporting domain + data
- `<app>/ui/<module>/lib/` — BLoC + Screen + State (one of each, plus barrel)
- `<app>/lib/di/` — DI modules (`@module`) and hand-maintained `injection.config.dart`
- `<app>/lib/routes/` — Router config and app navigation setup
- `<app>/test/features/<feature>/...` and `<app>/test/ui/<module>/...` — Mirrors `lib/`

## Allowed Paths

You may only edit/create under: `<app>/features/**`, `<app>/ui/**`, `<app>/lib/**`, `<app>/test/**`, `<app>/pubspec.yaml`, `<app>/analysis_options.yaml`, `<app>/l10n.yaml`

## Never Edit (Generated Files)

These are regenerated by tooling:
- `**/*.g.dart` — ObjectBox, json_serializable (use `dart run build_runner build`)
- `**/*.gr.dart` — auto_route (use `dart run build_runner build`)
- `**/app_localizations*.dart` — Generated from ARB (use `flutter gen-l10n`)
- `**/objectbox-model.json`

**Exception:** `lib/di/injection.config.dart` is hand-maintained — edit it directly.

## DI Registration — Critical Checklist

Adding a feature without registering crashes the app at runtime with `GetIt: Object/factory not registered`. Always:

1. Create `<app>/lib/di/<feature>_module.dart` with `@module` registrations (data source, repository, use cases)
2. Manually update `<app>/lib/di/injection.config.dart`:
   - Import the new module + feature package
   - Instantiate the module in `init()`
   - Register deps in order: data source → repository → use cases
   - Add the `_$<ModuleName>` class at the bottom
3. Add the feature package as a path dependency in `<app>/pubspec.yaml`
4. Add domain/data packages to any UI module's `pubspec.yaml` if it consumes them directly

**Use cases are always `@injectable` (factory) — never singleton or lazy-singleton.**

## Architecture Rules

- **Dependency direction:** feature → data → domain. Domain is pure Dart only.
- **Never import another feature's `data/` layer.** Cross-feature goes through `domain/` contracts.
- **Repositories never try/catch.** Data sources own `Result<T>` mapping via `HttpClient.execute` / `LocalClient.execute`. Repositories only transform (`.toDomain()`).
- One class per file. Filenames use `snake_case`, class names use `PascalCase`.
- Use cases: one per file, single public `call` method.

## UI Module Rules

Each UI module contains exactly three files plus a barrel:

- `<module>_state.dart` — Sealed base + `Loading`/`Success`/`Error` states
- `<module>_bloc.dart` — `Cubit<<Module>State>`, starts in `Loading`
- `<module>_screen.dart` — `@RoutePage()` widget, provides Cubit, uses `BlocBuilder`

Add router files if needed. Generated routes are regenerated automatically when annotations change.

## Localization

Every user-visible string goes through `AppLocalizations`:

1. Add key + `@key` metadata to `<app>/ui/common/lib/l10n/app_en.arb`
2. Add the same key with translation to `app_es.arb` AND `app_pt.arb`
3. Run `flutter gen-l10n` to regenerate `app_localizations.dart` (never edit by hand)
4. Use via `AppLocalizations.of(context)!.myKey` — import through `package:common/common.dart`

## Accessibility

- WCAG AA contrast: **4.5:1** normal text, **3:1** large text/UI
- Use `colorScheme` `on*` pairs for guaranteed contrast
- Icon-only buttons: wrap `Icon` in `Tooltip` or `Semantics(label: ...)`
- Decorative icons: `Icon(..., semanticLabel: null)` or `ExcludeSemantics`
- Touch targets ≥ **48×48 dp**
- Repeating `ListTile`s with chevrons: unique `Semantics(label: ...)` including item title

## Code Style

- **Formatting:** `dart format` runs automatically after edits
- **Always `const` constructors** where possible; `final` for non-reassigned variables
- **No `dynamic`** — explicit types only
- **Descriptive names** (not `r`, `d`, `m`, `e` — use `result`, `domainItems`)
- **Arrow syntax** (`=>`) for single-expression functions
- Filenames must be `snake_case` (no uppercase/hyphens)

## Testing

Mirror `lib/` under `test/` in the target Flutter submodule:

```
<app>/test/features/<feature>/{domain/usecases,data/{models,repositories}}/
<app>/test/ui/<module>/{pages,controllers}/
```

- Every public use case needs ≥1 unit test
- Mock repositories/data sources — never hit real network/storage
- File names: `<source>_test.dart`
- Run `flutter test` to verify before finishing

## Workflow

1. Read the feature spec/proposal from `research/`
2. Read the required-reading files listed above
3. Identify affected modules (feature domain/data, UI, DI, routes)
4. Implement in dependency order: domain → data → DI → UI → routes → tests
5. Use scaffolding commands (`/new-*`) wherever applicable
6. Run `flutter analyze` and `flutter test` to verify everything works

If analysis or tests fail, fix the cited issues before considering work done.
